【C1】core.py — 图片保存未指定格式，可能导致格式错误或崩溃
─────────────────────────────────────────────────────────────────────────────
位置: core.py:82
  cell.save(save_path)

问题:
  Pillow 的 Image.save() 依据文件扩展名推断格式。当 ext 为空或扩展名不被
  Pillow 识别时（例如用户模板修改了 ext 占位符为非法值），save() 会抛出
  ValueError 或保存为不可用文件。此外，对于某些模式（如 RGBA 保存为 JPEG），
  Pillow 会直接抛出 OSError。

建议:
  1. 在 save 前显式指定 format 参数:
       fmt = Image.registered_extensions().get(ext.lower(), 'PNG')
       cell.save(save_path, format=fmt)
  2. 或者在 split_image_core 入口处校验输出格式的合法性。
  3. 至少应将 cell.save() 包裹在 try/except 中，避免单个子图保存失败导致
     整个任务中断。

【C2】core.py — 扩展名拼接逻辑存在双重扩展名 Bug
─────────────────────────────────────────────────────────────────────────────
位置: core.py:65-79

问题:
  当用户模板中已经包含扩展名部分时（如 "{filename}_{index}.png"），
  第 78 行的检查 safe_name.lower().endswith(ext.lower()) 会通过，
  程序不再追加扩展名。但如果模板是 "{filename}_{index}"（默认），
  则 safe_name 值为 "test_rgb_01"，不含扩展名，会在第 79 行追加 ext。

  然而当模板为 "{filename}_{row}_{col}.{ext}" 时，safe_name 已经以
  ".png" 结尾，endswith 检查通过，不追加。但此时 safe_name 已经正确。

  真正的问题在于：模板中使用 {ext} 占位符时，ext.lstrip('.') 已经去掉了点，
  所以生成的是 "test_rgb_1_1.png"（正确），而模板不使用 {ext} 时，
  追加的 ext 包含点号，也是 "test_rgb_01.png"（正确）。两种情况都能工作，
  但中间状态不一致 —— ext 变量的含义在不同上下文中不同（有时有点有时无点）。

  更严重的是：第 41 行 ext = os.path.splitext(image_path)[1] or ".png"
  得到的 ext 包含点号（如 ".png"），但第 70、46 行传入 format 时用
  ext.lstrip('.') 去掉点号。第 78 行 endswith(ext.lower()) 则又期望带点。
  这种不一致极易在后续维护中引入 Bug。

建议:
  统一 ext 变量的语义，建议始终存储带点号的扩展名：
    ext = os.path.splitext(image_path)[1] or ".png"   # 保持不变
  然后在需要无点号的地方才 lstrip：
    name = config.template.format(..., ext=ext.lstrip('.'))
  在 endswith 和追加时始终使用带点号的 ext。

【C3】gui.py — 线程安全：对 tkinter 组件的非主线程访问
─────────────────────────────────────────────────────────────────────────────
位置: gui.py:345, 350

问题:
  self.root.after(0, lambda p=path, idx=i, total=len(paths):
      self.status_label.config(text=f"正在切割: {os.path.basename(p)} ({idx+1}/{total})"))
  self.root.after(0, lambda: self.progress.step(1))

  root.after() 本身是线程安全的（在 CPython 的 tkinter 实现中），但
  lambda 闭包捕获的变量 `path` 在 Python 中通过默认参数绑定是正确的。
  然而，self.progress.step(1) 的闭包没有捕获当前值，如果有并发调用，
  可能会出现进度条不准确。更重要的是，如果用户在任务运行中关闭窗口，
  root.after(0, ...) 的回调会尝试访问已销毁的 widget，导致 TclError。

建议:
  1. 在 finish_report 和所有 after 回调中检查 self.root.winfo_exists()
  2. 为窗口关闭事件绑定处理：self.root.protocol("WM_DELETE_WINDOW", self.on_close)
     在 on_close 中设置 stop_event 并等待线程结束后再销毁窗口。

【C4】cli.py — ProcessPoolExecutor 中 SplitConfig 的序列化问题
─────────────────────────────────────────────────────────────────────────────
位置: cli.py:84-91

问题:
  SplitConfig 是一个 @dataclass，默认可以被 pickle 序列化。但如果未来
  在 SplitConfig 中添加了不可序列化的字段（如函数、数据库连接等），或者
  在 Windows 上没有正确保护 __main__（当前已有保护），可能导致序列化失败。

  当前代码在功能上是正确的，但存在一个微妙问题：每个子进程都会重新导入
  core.py 和 models.py。如果这些模块有模块级副作用（如全局状态），
  可能引发问题。目前不存在，但需注意。

  此外，当用户输入的文件数量远大于 jobs 数时，所有任务会一次性提交到
  ProcessPoolExecutor，这意味着所有参数（包括图像路径）都会被序列化并
  保存在内存中。对于非常大的文件列表，这可能导致内存压力。

建议:
  考虑使用 executor.map() 替代 executor.submit()，或分批提交任务，
  以减少内存占用。当前实现对于一般场景足够。

【M3】core.py — 整数除法导致的像素对齐误差
─────────────────────────────────────────────────────────────────────────────
位置: core.py:53-56

问题:
  left   = int(j * img_width / config.cols)
  upper  = int(i * img_height / config.rows)
  right  = int((j + 1) * img_width / config.cols)
  lower  = int((i + 1) * img_height / config.rows)

  使用浮点除法再转 int（即 truncation），可能导致最后一个切片的右/下边界
  与原图实际像素不完全对齐。例如 img_width=100, cols=3 时：
    j=0: left=0,  right=int(33.33)=33
    j=1: left=33, right=int(66.67)=66
    j=2: left=66, right=int(100.0)=100
  
  切片宽度分别为 33, 33, 34，不均匀。这在大多数场景下可接受，
  但对于要求像素精确对齐的场景（如瓷砖地图、精灵表），可能产生视觉瑕疵。

建议:
  如果需要像素完美对齐，考虑使用整数除法:
    cell_w = img_width // config.cols
    cell_h = img_height // config.rows
    left   = j * cell_w
    right  = (j + 1) * cell_w if j < config.cols - 1 else img_width
  或者在文档中明确说明当前行为。

【M6】core.py — 异常捕获范围过窄
─────────────────────────────────────────────────────────────────────────────
位置: core.py:88

问题:
  except (OSError, ValueError) as e:

  Pillow 的 Image.open() 和 Image.save() 可能抛出多种异常:
  - PIL.UnidentifiedImageError (Pillow >= 8.0)
  - TypeError (如模式不兼容)
  - RuntimeError

    except Exception as e:
      return False, f"处理异常 ({type(e).__name__}): {str(e)}"
  如果需要区分可恢复错误和不可恢复错误，可以保留当前策略但添加更多类型。

【M7】gui.py — work_thread 中 lambda 闭包的 late binding 问题
─────────────────────────────────────────────────────────────────────────────
位置: gui.py:345, 350

问题:
  self.root.after(0, lambda p=path, idx=i, total=len(paths):
      self.status_label.config(...))

  第一个 lambda 通过默认参数正确捕获了 path, i, len(paths)——这是对的。

  但第二个 lambda:
    self.root.after(0, lambda: self.progress.step(1))
  
  如果 after 回调执行顺序与提交顺序不一致（极端情况），
  progress.step(1) 可能会在不正确的时刻执行。在当前单线程 UI 模型下
  不会出问题，但如果 future 版本改为异步，需要注意。

  此外，self.root.after(0, ...) 中的 0 延迟意味着回调会在下一个
  idle 时刻执行。如果工作线程提交大量回调（如处理 10000 张图），
  可能导致 UI 事件队列被淹没，界面冻结。

建议:
  对于大批量任务，考虑合并进度更新（如每 N 张更新一次 UI）。

【M8】cli.py — sys.path.insert(0, ...) 可能引入模块名冲突
─────────────────────────────────────────────────────────────────────────────
位置: cli.py:10

问题:
  sys.path.insert(0, str(Path(__file__).resolve().parent))

  这会将当前脚本目录插入 sys.path 最前面。如果该目录中存在与标准库或
  第三方库同名的文件（如 json.py、os.py 等），会优先导入该目录的文件，
  导致难以调试的问题。

建议:
  如果项目已经是一个正式包（有 __init__.py），建议使用相对导入或
  正式安装包后使用绝对导入。对于脚本使用场景，当前做法可以接受，
  但应在目录中避免放置与标准库同名的文件。

七、性能优化建议 (Performance)
================================================================================

【P1】gui.py — 缩略图使用 BILINEAR 重采样
  位置: gui.py:241
  display_img = self.thumb_img.resize((nw, nh), Image.Resampling.BILINEAR)
  
  对于向下缩放（缩略图→画布），LANCZOS 通常提供更高质量的输出。
  BILINEAR 更快但质量略低。对于实时预览场景，当前选择是合理的折衷，
  但可以考虑缓存 display_img 避免每次都重新 resize。

【P2】cli.py — ProcessPoolExecutor 启动开销
  对于少量文件（< 5 张），多进程的序列化和进程启动开销可能超过并行收益。
  建议: 当文件数 <= jobs 时才使用多进程，否则串行执行。

【P3】core.py — 每次都创建 output_dir
  位置: core.py:37-38
  os.makedirs(config.output_dir, exist_ok=True)
  在批量处理时，每个文件都会调用 os.makedirs，即使目录已存在。
  exist_ok=True 使其不会报错，但仍有系统调用开销。
  建议: 在 batch_process_images 中提前创建一次。
